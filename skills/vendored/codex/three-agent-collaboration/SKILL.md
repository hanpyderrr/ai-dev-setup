# 三 Agent 协作

## 目标

在 Codex 作为唯一主要交互窗口的前提下，把高 token 消耗的实现工作优先交给低成本 Agent，同时保留独立设计审核和可验证的质量门禁。

## 固定角色

- **Codex（主控）**：澄清目标、读取项目规则、拆解任务、维护计划、控制范围、整合结果、运行独立验证、向用户汇报。避免承担可安全委派的大批量编码。
- **Claude Code（设计/审核）**：在高影响方案实施前审查设计；实现完成后进行只读独立审核，重点检查需求遗漏、架构风险、回归风险和测试缺口。
- **DeepSeek Harness（实现/测试）**：按照已确认计划执行主要编码、测试、批量修改和低风险修复。必须返回改动文件与执行过的验证命令。
- **Kimi（可选研究）**：仅在长文档归纳、资料对照或大上下文检索确有收益时使用，不作为默认流水线节点。

## 启动门槛

满足以下任一条件时启用：

1. 用户明确要求“三 Agent 协作”。
2. 用户明确要求大型项目自动采用该分工，且任务符合至少一项：跨两个以上仓库或子系统；预计修改八个以上文件；同时需要设计、实现、测试和审核。

小型修复、单文件修改或纯问答不自动启用。若运行环境或更高优先级规则禁止委派，则由 Codex 本地完成并说明降级情况。

## 工作流

### 1. 范围与安全检查

Codex 先读取项目 `AGENTS.md`、工作区状态、入口文件和相关测试。明确允许修改的目录、禁止读取或提交的隐私数据，以及验收命令。不得把 API key、密码、Cookie、私有知识库内容放入提示、日志、补丁或提交。

### 2. 设计与分批计划

Codex 生成按依赖排序的计划和阶段门禁。涉及架构、公开 API、迁移、删除或高风险多文件修改时，先让用户确认方向。必要时由 Claude Code 对设计做一次聚焦审查。

每个实现批次必须包含：目标、允许范围、明确禁区、测试要求、完成定义和返回格式。优先把相互独立的批次并行处理；共享文件或有前后依赖的批次串行处理。

### 3. DeepSeek 实现

将已确认的有界批次交给 DeepSeek Harness。功能或缺陷修改遵循测试先行：先写并运行失败测试，再做最小实现，最后运行相关测试。不得提交、推送、删除用户文件、修改密钥或扩大范围，除非用户另有明确授权。

一次调用若超时、不可用或未产生可信输出，只允许一次聚焦重试；随后由 Codex 接管最小必要工作，不反复消耗额度。

### 4. Codex 独立验证

Codex 不直接采信子 Agent 的完成声明。逐项检查真实 diff、范围和隐私边界，并重新运行成本最低且最相关的测试、类型检查、构建或端到端验证。失败时记录证据，回到最小修复批次。

### 5. Claude 独立审核

验证通过后，给 Claude Code 精确的需求、改动文件列表和测试结果，要求只读审核。审核输出按严重度列出具体文件、位置、影响和建议；无问题时明确说明残余风险与测试盲区。

Claude 调用若超时或不可用，只尝试一次更小范围的审查；仍失败则由 Codex 完成严格自审，并向用户披露审核降级。

### 6. 阶段门禁

只有同时满足以下条件，才能开始下一阶段：

- 当前阶段验收项全部完成；
- 新鲜验证命令通过；
- 高严重度审核问题已修正并重新验证；
- 未发生隐私数据泄露或越权修改；
- 用户要求的确认点已经取得确认。

若用户明确说“审核通过再做下一阶段”，不得把实现完成等同于审核通过。

## 成本控制

- Codex 保持主要对话、决策与最终验收，不做可委派的大段重复编码。
- DeepSeek 使用短而完整的批次提示，避免反复读取整个仓库。
- Claude 只接收聚焦设计或改动文件进行审核，不承担常规实现。
- 不让多个 Agent 同时修改同一文件；Git 项目优先使用隔离 worktree，非 Git 项目通过文件范围串行隔离。
- 缓存和复用已有分析、测试输出与文件清单，避免重复扫描。

## 汇报格式

最终由 Codex 汇报：完成内容、各 Agent 实际贡献、验证证据、审核结论、残余风险，以及是否满足进入下一阶段的门禁。不得在汇报中输出任何密钥或私有知识库正文。
